# Research: Session Management & Continuation

**Feature**: 012-session-management  
**Date**: 2026-02-04  
**Phase**: 0 (Technology Analysis)

## Overview

This document consolidates research findings for implementing session management and continuation in Orchestra. All technical unknowns from the specification have been investigated and resolved.

---

## 1. Message Storage Strategy

### Decision: Normalized Table vs JSON Blob

**Chosen**: Normalized `session_messages` table with individual rows per message

**Rationale**:

- ✅ Enables efficient queries (e.g., "find sessions mentioning X")
- ✅ Per-message token tracking for analytics
- ✅ Pagination support for UI (load messages in chunks)
- ✅ Better for conversation analysis queries
- ✅ Aligns with SQLite best practices for relational data

**Alternatives Considered**:

1. **JSON blob in agent_sessions.conversation_state**
   - ❌ Rejected: No queryability, no pagination, bloats session table
   - Would require loading ALL messages for ANY query
   - No per-message analytics

2. **Hybrid: Recent messages in table, archived in JSON**
   - ❌ Rejected: Complexity not justified by benefit
   - Would need migration logic between storage layers
   - Resume would need to handle both formats

**Best Practices from Research**:

- SQLite handles millions of small rows efficiently (messages ~1-5KB each)
- Indexes on (session_id, message_index) enable fast ordered retrieval
- JSON functions (json_extract) available if structured queries needed later

## 2. Async Message Persistence Pattern

### Decision: Fire-and-forget with error logging

**Chosen**: Async database insert from AgentSession.addMessage(), log errors but don't throw

**Rationale**:

- ✅ Agent execution MUST NOT be blocked by database I/O
- ✅ Session persistence is observability, not critical path
- ✅ Lost messages are acceptable (events provide backup timeline)
- ✅ Matches existing pattern for event insertion

**Implementation Pattern**:

```typescript
// AgentSession.addMessage()
addMessage(message: AgentMessage): void {
  this.messages.push(message); // In-memory (synchronous)
  this.updateActivityTimestamp();

  // Async persistence (fire-and-forget)
  SessionMessageRepository.insertMessage(this.workspaceRoot, {
    session_id: this.id,
    role: message.role,
    content: message.content,
    iteration: message.iteration
  }).catch(err => {
    console.error(`[SessionPersistence] Failed to insert message: ${err.message}`);
    // Don't throw - agent continues execution
  });
}
```

**Edge Case Handling**:

1. **Database locked (SQLITE_BUSY)**:
   - Log error, continue execution
   - Retry not implemented initially (messages are append-only)
   - Future: Could add retry queue if frequent failures observed

2. **Disk full**:
   - Insert fails, logged, agent continues
   - User notification via extension (low disk space warning)

3. **Race condition (concurrent inserts)**:
   - message_index auto-generated by repository (MAX + 1)
   - SQLite transaction isolation prevents gaps

**Best Practices from Research**:

- Node.js async patterns: Promise.catch() for fire-and-forget
- SQLite WAL mode (already enabled) allows concurrent reads during writes
- No need for message queue initially (single-threaded agent execution)

## 3. Token Counting Integration

### Decision: Use existing ContextManager.estimateTokens()

**Chosen**: Call ContextManager at message insert time, store result in token_count column

**Rationale**:

- ✅ Reuses proven token estimation logic (tiktoken-based)
- ✅ Immutable - token count doesn't change retroactively
- ✅ Fast queries for sprint analytics (SUM(token_count))
- ✅ Aligns with existing context compaction workflow

**Integration Point**:

```typescript
// SessionMessageRepository.insertMessage()
export function insertMessage(
  workspaceRoot: string,
  message: MessageInput,
): SessionMessage {
  const db = getDb(workspaceRoot);

  // Estimate tokens using existing ContextManager
  const tokenCount = ContextManager.estimateTokens(message.content);

  const id = generateId();
  const messageIndex = getNextMessageIndex(db, message.session_id);

  db.prepare(
    `
    INSERT INTO session_messages (id, session_id, message_index, role, content, token_count, timestamp, iteration)
    VALUES (?, ?, ?, ?, ?, ?, ?, ?)
  `,
  ).run(
    id,
    message.session_id,
    messageIndex,
    message.role,
    JSON.stringify(message.content),
    tokenCount,
    new Date().toISOString(),
    message.iteration,
  );

  return {
    id,
    ...message,
    message_index: messageIndex,
    token_count: tokenCount,
  };
}
```

**Token Estimation Accuracy**:

- ContextManager uses tiktoken (OpenAI's official library)
- Accuracy: ±5% for text content
- Structured content: Estimates JSON serialization overhead
- Acceptable for analytics (exact billing from LLM API logs)

**Best Practices from Research**:

- Store estimated tokens, not actual (actual only known after LLM response)
- Use cl100k_base encoding (GPT-4, Claude 3 compatible)
- For tool calls: Count tool name + serialized arguments
- For tool results: Count full result text

## 4. Session Continuation Architecture

### Decision: New session record with parent_session_id (immutable audit trail)

**Chosen**: Create new session on continuation, link via parent_session_id

**Rationale**:

- ✅ Original session preserved as immutable record (audit trail)
- ✅ Enables "undo continuation" (revert to parent state)
- ✅ Tracks continuation count (failure loop detection)
- ✅ Clear lineage: which orchestrator session triggered continuation
- ✅ NO message inheritance (maintains agent separation)

**Continuation Workflow**:

```typescript
// High-level flow
orchestratorSession = verifyTask(taskId)
orchestratorSession.judge → FAIL

// Get latest implementor session for this task
implementorSession = getLatestImplementorSession(taskId)

// Continue it with feedback
continuedSession = continueSession(
  sessionId: implementorSession.id,
  prompt: "Verification failed: Missing password hashing. Please add bcrypt.",
  stage: "IMPLEMENT_FIX"
)

// Result: New session record
continuedSession.id = "session-new-id"
continuedSession.parent_session_id = implementorSession.id
continuedSession.attempt = implementorSession.attempt + 1
continuedSession.messages = implementorSession.messages + [new_user_message]
```

**Database Schema for Continuation**:

```sql
-- agent_sessions table (modified)
ALTER TABLE agent_sessions ADD COLUMN parent_session_id TEXT;
ALTER TABLE agent_sessions ADD COLUMN attempt INTEGER DEFAULT 1;
ALTER TABLE agent_sessions ADD COLUMN is_continued INTEGER DEFAULT 0;
ALTER TABLE agent_sessions ADD COLUMN continued_at TEXT;
ALTER TABLE agent_sessions ADD COLUMN continuation_count INTEGER DEFAULT 0;

CREATE INDEX idx_sessions_parent ON agent_sessions(parent_session_id);
```

**Alternative Considered: Mutate original session**

- ❌ Rejected: Loses audit trail, no way to track "how many times continued"
- ❌ Can't distinguish original attempt from fixes
- ❌ Harder to implement "undo" functionality

**Best Practices from Research**:

- Self-referential foreign keys common in SQLite (parent_session_id → id)
- Recursive CTE for traversing continuation chains: `WITH RECURSIVE chain AS ...`
- Limit continuation depth (prevent infinite loops): MAX 5 levels

## 5. Agent Separation Boundary Enforcement

### Decision: Session continuation does NOT inherit parent agent's messages

**Chosen**: When orchestrator continues implementor session, implementor sees ONLY its own history + new prompt

**CRITICAL Architectural Principle**:

- Orchestrator (Session A) and Implementor (Session C) are SEPARATE AGENTS
- Session C must NEVER see Session A's verification process
- parent_session_id tracks LINEAGE ONLY (which orchestrator triggered continuation), NOT message inheritance

**Continuation Message Flow**:

```typescript
// Session A (orchestrator verifying Task 5)
messages: [
  { role: "system", content: "You are an orchestrator..." },
  { role: "user", content: "Verify Task 5 implementation" },
  {
    role: "assistant",
    content: "Checking... FAILURE: Missing password hashing",
  },
];

// Session C (implementor implementing Task 5)
messages: [
  { role: "system", content: "You are an implementor..." },
  { role: "user", content: "Implement user authentication" },
  { role: "assistant", content: "I created auth.ts with login/logout..." },
  // ... 12 more messages
];

// continueSession(sessionId: 'session-C', prompt: 'Add password hashing')
// Result: Session C_continued
messages: [
  // ALL 15 ORIGINAL SESSION C MESSAGES (implementor's history)
  { role: "system", content: "You are an implementor..." },
  { role: "user", content: "Implement user authentication" },
  { role: "assistant", content: "I created auth.ts..." },
  // ... (all implementor messages)

  // PLUS NEW PROMPT:
  { role: "user", content: "Add password hashing", iteration: 16 },

  // NO SESSION A MESSAGES - orchestrator verification is hidden
];
```

**Verification of Separation in Code**:

```typescript
export function continueSession(
  workspaceRoot: string,
  sessionId: string,
  continuationPrompt: string,
  stage: SessionStage,
): AgentSession {
  const db = getDb(workspaceRoot);
  const parentSession = getSession(workspaceRoot, sessionId);

  // CRITICAL: Load messages ONLY from parent session (same agent)
  const parentMessages = getSessionMessages(workspaceRoot, sessionId);

  // Create new session (inherits role from parent)
  const newSession = createSession(workspaceRoot, {
    role: parentSession.role, // SAME agent type
    task_id: parentSession.task_id,
    sprint_id: parentSession.sprint_id,
    stage: stage,
    parent_session_id: sessionId, // Lineage tracking
    attempt: parentSession.attempt + 1,
  });

  // Copy parent messages to new session
  for (const msg of parentMessages) {
    insertMessage(workspaceRoot, {
      session_id: newSession.id,
      role: msg.role,
      content: msg.content,
      iteration: msg.iteration,
    });
  }

  // Add continuation prompt
  insertMessage(workspaceRoot, {
    session_id: newSession.id,
    role: "user",
    content: continuationPrompt,
    iteration: parentMessages.length + 1,
  });

  return newSession;
}
```

**Best Practices from Research**:

- Trust boundaries enforced at data layer (repository functions)
- UI can visualize session lineage without exposing cross-agent messages
- Database schema allows parent_session_id across different roles (lineage tracking)
- Session chain queries filter by role to prevent leakage

## 6. Performance Optimization Strategies

### Decision: Indexed queries + pagination for large conversations

**Chosen**: Composite index on (session_id, message_index) for ordered retrieval

**Performance Targets**:

- Message insert: <5ms p95
- Message retrieval (100 messages): <500ms
- Token aggregation (50 sessions): <100ms

**Index Strategy**:

```sql
-- Primary index for ordered message retrieval
CREATE INDEX idx_messages_session_seq ON session_messages(session_id, message_index);

-- Secondary index for time-based queries
CREATE INDEX idx_messages_timestamp ON session_messages(timestamp);

-- Session continuation chain traversal
CREATE INDEX idx_sessions_parent ON agent_sessions(parent_session_id);

-- Task → sessions lookup
CREATE INDEX idx_sessions_task_stage ON agent_sessions(task_id, stage);
```

**Query Optimization**:

```sql
-- Fast: Uses idx_messages_session_seq
SELECT * FROM session_messages
WHERE session_id = ?
ORDER BY message_index ASC;

-- Fast: Uses idx_sessions_task_stage
SELECT * FROM agent_sessions
WHERE task_id = ? AND stage = 'IMPLEMENT'
ORDER BY created_at DESC
LIMIT 1;

-- Fast: Recursive CTE with idx_sessions_parent
WITH RECURSIVE chain AS (
  SELECT * FROM agent_sessions WHERE id = ?
  UNION ALL
  SELECT s.* FROM agent_sessions s
  JOIN chain c ON s.parent_session_id = c.id
)
SELECT * FROM chain;
```

**UI Pagination Pattern**:

```typescript
// Load first 50 messages
const messages = getSessionMessages(sessionId, { offset: 0, limit: 50 });

// Virtualized scrolling loads more as needed
const nextBatch = getSessionMessages(sessionId, { offset: 50, limit: 50 });
```

**Best Practices from Research**:

- SQLite EXPLAIN QUERY PLAN to verify index usage
- Composite indexes cover both WHERE and ORDER BY clauses
- LIMIT queries prevent full table scans for large sessions
- Recursive CTEs efficient for tree traversal (continuation chains)

## 7. Database Migration Strategy

### Decision: Two migrations for backward compatibility

**Chosen**:

- Migration 018: Create session_messages table
- Migration 019: Alter agent_sessions (add stage, parent_session_id, etc.)

**Migration 018: session_messages table**

```sql
-- 018-session-messages-table.sql
CREATE TABLE IF NOT EXISTS session_messages (
  id TEXT PRIMARY KEY,
  session_id TEXT NOT NULL,
  message_index INTEGER NOT NULL,
  role TEXT NOT NULL CHECK(role IN ('system', 'user', 'assistant')),
  content TEXT NOT NULL,
  token_count INTEGER,
  timestamp TEXT NOT NULL,
  iteration INTEGER NOT NULL,
  FOREIGN KEY (session_id) REFERENCES agent_sessions(id) ON DELETE CASCADE
);

CREATE INDEX idx_messages_session_seq ON session_messages(session_id, message_index);
CREATE INDEX idx_messages_timestamp ON session_messages(timestamp);
```

**Migration 019: agent_sessions columns**

```sql
-- 019-session-stage-fields.sql
ALTER TABLE agent_sessions ADD COLUMN stage TEXT CHECK(stage IN ('PREPARE', 'IMPLEMENT', 'VERIFY', 'IMPLEMENT_FIX', 'CODE_REVIEW', 'GENERAL'));
ALTER TABLE agent_sessions ADD COLUMN parent_session_id TEXT;
ALTER TABLE agent_sessions ADD COLUMN attempt INTEGER DEFAULT 1;
ALTER TABLE agent_sessions ADD COLUMN is_continued INTEGER DEFAULT 0;
ALTER TABLE agent_sessions ADD COLUMN continued_at TEXT;
ALTER TABLE agent_sessions ADD COLUMN continuation_count INTEGER DEFAULT 0;

CREATE INDEX idx_sessions_stage ON agent_sessions(task_id, stage);
CREATE INDEX idx_sessions_parent ON agent_sessions(parent_session_id);
```

**Backward Compatibility**:

- Existing sessions without stage: NULL allowed (legacy sessions)
- Queries handle NULL stage gracefully: `WHERE stage IS NULL OR stage = 'GENERAL'`
- No data migration needed (new columns default to NULL/0)

**Testing Strategy**:

1. Run migrations on empty database (new workspace)
2. Run migrations on existing database with 50+ sessions
3. Verify existing sessions queryable after migration
4. Verify CASCADE DELETE works for retention policy

**Best Practices from Research**:

- SQLite ALTER TABLE only supports ADD COLUMN (no DROP/RENAME)
- CHECK constraints enforce enum values at database level
- Foreign key with ON DELETE CASCADE enables automatic cleanup
- Separate migrations for table creation vs schema changes

## 9. Retention Policy Integration

### Decision: Cascade delete with sessions (no separate cleanup)

**Chosen**: ON DELETE CASCADE foreign key constraint handles message cleanup

**Integration with Existing Retention**:

Orchestra's retention policy (TD-033):

- Keep last 3 completed tasks per sprint
- Purge older sessions automatically
- Triggered by task completion

**Implementation**:

```sql
-- Foreign key in session_messages table
FOREIGN KEY (session_id) REFERENCES agent_sessions(id) ON DELETE CASCADE
```

When session deleted → SQLite automatically deletes all messages → No orphaned rows

**Monitoring Database Size**:

```sql
-- Query to estimate database growth
SELECT
  COUNT(*) as message_count,
  SUM(LENGTH(content)) / 1024 / 1024 as content_mb,
  SUM(token_count) as total_tokens
FROM session_messages
WHERE session_id IN (
  SELECT id FROM agent_sessions WHERE sprint_id = ?
);
```

**Expected Growth**:

- 50 sessions/sprint × 100 messages/session × 2KB/message = 10MB
- Within acceptable range (<50MB per sprint)

**Best Practices from Research**:

- SQLite VACUUM command to reclaim space after deletions
- Retention policy runs in background (doesn't block workflow)
- Monitor via PRAGMA page_count to track database file size

## 10. Error Handling & Recovery

### Decision: Graceful degradation (sessions work without message history)

**Chosen**: Message persistence is observability layer, not critical path

**Failure Scenarios**:

1. **Message insert fails (database locked)**:
   - Agent continues execution (messages in-memory)
   - Error logged to console
   - User notification: "Session history may be incomplete"
   - Events still captured (UI still works)

2. **Message retrieval fails (corrupted database)**:
   - Resume operation falls back to event reconstruction
   - Warning displayed: "Conversation history unavailable"
   - Agent can still start fresh with task context

3. **Session continuation with missing parent**:
   - Error thrown: "Parent session not found"
   - UI offers "Start new session" option
   - Prevents broken continuation chains

**Recovery Mechanisms**:

```typescript
// Graceful message retrieval
export function getSessionMessages(
  workspaceRoot: string,
  sessionId: string,
): SessionMessage[] {
  try {
    const db = getDb(workspaceRoot);
    return db
      .prepare(
        `
      SELECT * FROM session_messages 
      WHERE session_id = ? 
      ORDER BY message_index ASC
    `,
      )
      .all(sessionId) as SessionMessage[];
  } catch (err) {
    console.error(`Failed to load messages for session ${sessionId}:`, err);
    return []; // Return empty array, agent handles gracefully
  }
}

// Resume with fallback to events
export async function resumeSession(sessionId: string): Promise<AgentSession> {
  const messages = getSessionMessages(workspaceRoot, sessionId);

  if (messages.length === 0) {
    // Fallback: Reconstruct from events
    const events = getSessionEvents(workspaceRoot, sessionId);
    return reconstructSessionFromEvents(events);
  }

  return reconstructSessionFromMessages(messages);
}
```

**Best Practices from Research**:

- Try-catch around all database operations
- Log errors with context (session ID, operation type)
- Return empty/null for non-critical failures
- Throw errors only for unrecoverable states
