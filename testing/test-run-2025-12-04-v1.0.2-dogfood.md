## Issues Found

### Issue 1: Unclear Manifest Validation Error

**Command**: `npx orchestra status`
**Expected**: Clear error message explaining what's wrong with manifest
**Actual**: Only shows `Validation failed for: <path>` with no details

**Error Output**:
```
✗ Error: Validation failed for: E:\...\manifest.yaml
Command exited with code 1
```

**Root Cause**: The manifest had `meta:` instead of `sprint:` and used `depends_on:` instead of `dependencies:`. The error message doesn't show Zod validation details.

**Suggested Fix**: Display Zod parse errors in the CLI output so users know which fields are wrong.

**Severity**: MINOR (usability)
**Status**: LOGGED

### Issue 2: Handover Path Inconsistency

**Command**: `npx orchestra prepare --task 1`
**Expected**: Handover files in `.orchestra/handover/` (shared neutral zone per original design)
**Actual**: Handover files placed in `.orchestra/implementor/handovers/`

**Evidence**:
- Case study (original design): `.orchestra/handover/current-task.md`
- CLI default config: `paths.handovers: "implementor/handovers"`
- Creates: `.orchestra/implementor/handovers/current-task.md`

**Impact**:
1. Breaks separation of concerns - handover is meant to be neutral territory
2. Implementor agents looking in `handover/` won't find files
3. `.orchestra/handover/` folder exists but remains empty (only `.gitkeep`)

**Original Architecture (from case study)**:
```
.orchestra/
├── handover/           # SHARED - neutral handover zone
│   ├── current-task.md
│   └── verification/
├── implementor/        # PRIVATE - implementor workspace
│   └── .implementor-only/
└── orchestrator/       # PRIVATE - orchestrator workspace
    └── .orchestrator-only/
```

**Current CLI Behavior**:
```
.orchestra/
├── handover/           # UNUSED (empty)
├── implementor/
│   └── handovers/      # ← Files placed here instead
└── orchestrator/
```

**Severity**: MAJOR (architectural inconsistency)
**Status**: FIXED

**Fix Applied**:
- Changed default `paths.handovers` from `implementor/handovers` to `handover`
- Updated `src/core/types.ts` (DEFAULT_CONFIG + PathsConfigSchema)
- Updated `src/core/prepare.ts` (file generation messages)
- Updated `src/commands/prepare.ts` (console output)
- Updated tests in types.test.ts, signal.test.ts, config.test.ts, prepare.test.ts
- All 346 tests pass

### Issue 3: --spec Flag Does Nothing / No Manifest Generation Guidance

**Command**: `npx orchestra init --spec spec/implementation/phase-2-mcp`
**Expected**: Either auto-generate manifest from spec OR provide clear guidance on how to create one
**Actual**: 
1. `--spec` flag is accepted but completely ignored
2. Init tells user to "See docs/manifest-schema.md" which doesn't exist
3. No example manifest, no schema docs, no template

**Impact**:
- A new orchestrator agent has NO IDEA how to create the manifest
- The spec path provided is not used at all
- Documentation reference is broken

**Evidence**:
```
Next steps:
  1. Create a manifest: Create .orchestra/manifest.yaml manually
     (See docs/manifest-schema.md for format)  ← FILE DOESN'T EXIST
```

**What a new agent would need to know**:
1. Manifest schema (version, sprint object, tasks array)
2. Task field mappings (id, title, description, status, category, dependencies, speckit_task_ref)
3. How to map spec task IDs (2.1, 2.2) to manifest IDs (1, 2, 3)
4. Valid enum values (status: PENDING/IMPLEMENT/COMPLETE, category: INFRASTRUCTURE/INTEGRATION/VISUAL)

**Options**:
- A) Fix init to parse spec and auto-generate manifest (complex, fragile)
- B) Create `orchestra import-spec` command (modular, can iterate)
- C) Create missing docs + emit template manifest during init (minimal, unblocks agents)

**Severity**: MAJOR (blocks new orchestrator agents)
**Status**: FIXED

**Agreed Fix Plan**:
1. Store `spec_path` in orchestra.yaml when `--spec` flag provided
2. Generate template manifest.yaml with TODOs pointing to spec
3. Enhance status command to show next step when manifest incomplete/missing
4. Update init console output with clearer instructions

**Fix Applied**:
1. `src/core/types.ts`: Added `spec_path` to OrchestraConfigSchema
2. `src/commands/init.ts`: 
   - Store spec_path in config when --spec provided
   - Generate manifest template with TODOs referencing spec
   - Enhanced showSuccess() with clearer next steps
3. `src/commands/status.ts`:
   - Added `isManifestPlaceholder()` to detect template manifests
   - Added `showManifestGuidance()` with helpful instructions
   - Status now shows guidance when manifest needs configuration
4. All 346 tests pass

**Verification**:

npx orchestra init --spec spec/implementation/phase-2-mcp
# Output shows: "Your spec is at: spec/implementation/phase-2-mcp"

# Status detects placeholder and shows guidance

# Output shows: "Manifest needs configuration" with detailed steps
